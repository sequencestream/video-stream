# 脚本导入（intake）

## 它补的是哪个洞

流水线下游的一切——TTS、字幕、渲染缓存、增量重编译——都定义在 seg 图上，但在此之前没有
任何东西能从作者真正拥有的东西（一段写好的口播稿）造出这张图。调用方只能手写 seg JSON
并手算 `duration_budget`，而预算算错不是取整误差，是句尾被切掉的成片。

`internal/intake` 就是这一步：标题 + 口播稿 → 已 seal、通过 `Validate` 的 `model.Project`。

## 预算是测出来的

这是本包唯一真正重要的决策。

渲染管线在 mux 阶段按 `DurationBudget.TargetMS()`（区间中点）裁剪视频轨，而音轨长度是 TTS
的实际输出。两者不一致时，`ExecOutputValidator` 只校验容器时长，**不校验音画对齐**——所以
预算猜错不会让渲染失败，只会让最后半句话消失在成片里。

因此导入时每句都先真实合成一次，用实测时长作为预算中点，`NewDurationBudget` 再展开成 ±8%
区间。代价是导入耗时与稿子长度成正比（十句约 15 秒），换来的是音画天然对齐。

### 为什么不用 `audio.TTS` 接口

`EdgeTTS.Synthesize` 会把音频**时间伸缩**到 seg 的预算里，超过 ±8% 就返回
`ErrNeedsWordCountChange`。拿一个占位预算去问它「这句多长」，它要么把答案拉回占位值，要么
直接报错——它回答不了预算存在之前的问题。

所以 `EdgeTTS` 额外提供 `RawDurationMS`：跑同一条合成链路，但停在时间伸缩之前。
`audio.TTSProbe` 包装它，`intake.Prober` 只依赖「文本进、毫秒出」这一个窄接口。

stub 通路（`VS_TTS_PROVIDER=stub`）用 `audio.EstimateProbe` 按字数估算。它给出的数字是
似真的，不是真的：stub 模式本来就不产生可播放音频，那里的预算永远不必和一段波形对齐。

## 切句规则

按顺序执行，先断句、再切长、最后并短：

1. **句末标点断句**：`。！？；!?;…` 与空行。标点留在句尾——文本要交给 TTS，停顿正是从这些
   标记读出来的。
2. **超长句在最后一个从句断点处切**：`，,、：:—`，上限默认 48 字（约 12 秒普通话）。
3. **过短句并入前一句**：下限默认 8 字。并入后若超过上限则不并——那只会把第 2 步的问题
   重新造出来。首句过短没有前句可并，则向后并。

**找不到从句断点的超长句保持原样**。中间硬切会把一个半句丢给 TTS，它会用错误的语调读完：
太长还能看，读断了不能。

字数按 rune 计，因为目标语料是 CJK，一个 rune 大致就是一个音节。

## 导入产物互不依赖

生成的 seg 没有 `depends_on`。旁白句子之间不存在解析顺序，而线性依赖链会让「改第一句」
沿反向边失效后面所有 seg——正是增量重编译要消除的成本。

## 工程 id

缺省由标题派生：小写、非字母数字折叠成 `-`、截断到 24 字符，再拼 UTC 时间戳。id 会成为
`media/<project_id>/` 与 `output/<project_id>/` 的路径段，所以强制 ASCII；中文标题会退化成
纯时间戳，这是可接受的——需要可读 id 时显式传 `-id`。

## 明确不做

- **LLM 改写口播稿**。`vs project create` 一字不改地照搬输入。改写是 `/v1/script/polish`
  的职责，两件事混在一起会让「我写的稿子去哪了」变成一个没法回答的问题。
- **并发探测**。十句串行约 15 秒，够用；并发要处理 edge-tts 的限流，而这个成本目前买不到
  什么。
- **按语义切句**。标点是作者已经给出的显式停顿信号，语义切分需要模型，会把一个确定性的
  纯函数变成一次网络调用。
- **句间停顿**。`Breath` 枚举存在，但音频引擎当前不消费 `PauseMS`，所以导入不标注它——
  标了会让人以为渲染会照做。
